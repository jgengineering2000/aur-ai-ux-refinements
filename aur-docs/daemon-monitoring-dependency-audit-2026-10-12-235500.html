Daemon Monitoring: Mtime-Driven Lifecycle Architecture

2026-10-12. Architectural audit and redesign for log channel discovery and metrics monitoring in aur/server/server.py. Formulates the owner's exact event-driven model: mtime update as the sole driver of writer discovery, targeted PID+fd monitoring while the descriptor remains held, and an isolated close/exit rescan before returning to dormancy.

1. The Foundation: The Owner's Direct Model

"As I see it the critical driver is the mtime being updated. That is the event. We don't care who the writer is until the file is written. So, ultimately we need to notice a file has changed. Why? There are some applications which will write to the same log file until it reaches a certain size, but may not run every day. If we care who those writers are we can look it up after it's been written and monitor the PID as long as it has the particular monitored fd open. If the process exits or if it simply closes the fd we can stop looking at the PID. At that point we scan to see if anyone else has it open. If they don't we go back to waiting until the file moves again. Then we find who has it open and go back to monitoring until the PID(s) close the fd (or the PID exits)."

2. The Flaw in the Previous Approach

  • The Inverted Assumption: The prior implementation assumed that every file in daemon_dir needed continuous classification of its writer status on every periodic tick. When a file was quiet and unheld, it repeatedly ran _LIB_FDUSER_FIND across all 545 processes and 4,800 open descriptors in the OS to prove nobody was writing to it.
  • The Missing Precedent: Proving that a file has no writer is an $O(\text{all system FDs})$ operation. Running that operation periodically on files that have not received any writes is pure waste.
  • The Correction: We do not care who holds a file open until that file is actually written to! An idle log file that hasn't changed requires zero `/proc` introspection, even if an application holds an open file descriptor for days without writing.

3. The State Machine & Deterministic Lifecycle

Each tracked log file exists in one of two states: DORMANT or MONITORED.

4. The Lifecycle in Detail

Phase 1: Dormancy & Notice of Change

  • When a file has no active writers (such as mti-vfs-crash.log or an idle log), it enters DORMANT with its current st_mtime_ns as baseline_mtime.
  • As long as no process writes to the file, mtime remains identical to baseline_mtime.
  • No `/proc` scans occur. The periodic 1-second /procstats endpoint bypasses all dormant files completely.

Phase 2: Post-Write Discovery

  • When an application writes to the log, the kernel updates st_mtime.
  • The change is detected either by the inotify loop (IN_MODIFY) or on the next periodic check if mtime != baseline_mtime.
  • Now, and only now, do we look up the writer:
    • Call fduser_find_writers for this specific file.
    • Because the application was just writing, the process and fd are actively open, allowing the native scan to early-exit rapidly on the writer.
    • If a writer is found: record (pid, fd) and transition the file to MONITORED.
    • If no writer is found (e.g. a short script ran, appended, and closed before the check): record the new mtime as baseline_mtime and stay in DORMANT.

Phase 3: Targeted Monitoring

  • While in MONITORED, we know the exact pid and target_fd.
  • On each 1-second metric tick:
    • Verify os.kill(pid, 0).
    • Verify /proc/{pid}/fd/{target_fd} points to our file and is writable (via fdinfo flags).
    • If valid, read CPU and RSS metrics.
  • Cost: Exactly 1 kill syscall + 1 readlink + 1 stat. Total duration: ~15 microseconds. Zero full-system `/proc` walking.

Phase 4: Close / Exit and Final Rescan

  • When the monitored process exits or closes target_fd:
    • Stop tracking that PID.
    • Run an isolated rescan: Check if any other process currently has this file open for writing.
    • If another writer exists: Adopt the new (pid, fd) and remain MONITORED.
    • If no other writer exists: Update baseline_mtime = current_mtime and transition back to DORMANT.
  • Once back in DORMANT, no further scans occur until the file moves again.

5. Why This Solves the Edge Cases

  • Intermittent / Rotating Daemons: An application that writes to a log once per day or once an hour sits in DORMANT for 23 hours and 59 minutes. It consumes zero CPU while idle. The moment it writes, it is discovered, monitored during execution, and cleanly retired to DORMANT when it closes its descriptor.
  • Dead Crash Logs & One-Shots: Crash logs from days ago (e.g. mti-thumb-probe-crash.log, restoremeta-crash.log) will never have their mtime advance. Under this design, they are placed in DORMANT once and never inspected in `/proc` ever again.
  • Multiple Writers: If a secondary process or worker also writes to the log, the close-rescan pass explicitly checks whether anyone else has the file open before dropping monitoring, preserving the invariant that a file is only unmonitored when its last writer closes.
