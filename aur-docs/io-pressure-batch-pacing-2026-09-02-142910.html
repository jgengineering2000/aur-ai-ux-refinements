I/O-Pressure Batch Pacing

STATUS: DEFERRED — design accepted as potentially useful; implementation postponed by owner ruling (2026-09-02) until a less critical phase of development. Nothing here is Implemented or Exercised; every section is Designed only.

Owner ruling — why this is parked

The owner judged the design potentially useful but quite complex, naming four risk classes: arbitrary tuning behavior (the pause threshold and hysteresis have no principled derivation yet, only a measurement plan), vulnerability to freezes (a job left frozen by a crashed or wedged gate is a hung build with no visible cause), performance regressions (pause time distorting timing bands, batch throughput lost to over-triggering), and catastrophic cascade failures (a frozen job holding a lock — cargo's, the harness's, a FUSE mount — while everything behind it queues). Deferred until a less critical phase; the no-root constraint below stands regardless.

Problem

User scenario: a video plays (or any latency-sensitive foreground app runs) while gate-admitted batch work — a build, a test run, a benchmark — is executing. Expected: foreground stays smooth, since batch runs at nice 15+. Instead: the video stutters. Why: niceness governs only the CPU scheduler; the batch job's reads and writes queue at the block device ahead of the player's, and nothing in the current scheduler (the MTI_NICE_* band applied by the gates) touches that queue.

Design

Everything lands in mti-gate (MTI rust/launcher/src/bin/mti-gate.rs), the one gate that already supervises its job (spawn-and-wait); rustc-gate and cc-gate keep their deliberate exec and inherit the behavior via the cgroup when a build stage is itself wrapped by mti-gate. The nice band is untouched — this is a parallel axis.

Conditions — when each command runs

mti-gate invoked
├─ systemd user manager reachable?  (probe once)
│   ├─ yes → spawn in scope; supervision loop armed
│   └─ no  → spawn directly as today; event: "note … no slice isolation — pause/resume disabled"
└─ each 500 ms poll while job runs:
    ├─ child exited?            → done event, exit
    ├─ TERM/INT flagged?        → systemctl --user stop <scope>, reap, done event
    ├─ running & unfrozen:  fg stall ≥ threshold, 2 polls → freeze + pause event
    └─ running & frozen:    fg stall ≤ clear level        → thaw  + resume event

Runtime dependencies added: systemd-run, systemctl (present on any systemd host) and one /sys file — no crates; the launcher stays dependency-free.

Known limits (honest scope)

  • Reads and sync writes from batch are paused within ~1 s of a foreground stall; a continuous-deprioritization scheme (io.latency) would have needed root.
  • Writeback backlog: a freeze stops new dirty pages, but pages already queued drain at full rate for a few seconds — the collision is transient, not eliminated.
  • Coverage is only jobs the gates launched; anything started outside them is invisible to this mechanism.
  • The freezer suspends processes holding locks (cargo's target-dir lock, the test-harness lock, FUSE requests in flight). Bounded by the thaw in the normal case — this is the owner's cascade-failure risk when the thaw never comes.

Resume checklist (for the future session that picks this up)

  • Re-verify the host facts (block scheduler, delegation, PSI paths) — they are environment, not code, and can have moved.
  • Run the PSI observation first; derive threshold + hysteresis from the measured stall fraction during real stutter.
  • Design the freeze-orphan safeguard before the freeze itself: gate crash must thaw/stop the scope (owner risk #2/#4) — e.g. scope RuntimeMaxSec or a startup census that finds and disposes of stale mti-batch.slice members, per the P8 owner-lifecycle rule.
  • Fail-first tests beside the existing gate suites (gate_supervision.rs, gate_reporting.rs); timing-band split (elapsed vs paused) lands with the feature, not after it.
