Machine Row & Policy Ownership — Implementation Plan

Status: DRAFT for owner review · 2026-09-01 · Scope: AUR (primary) + MTI (consumer) · Trigger: AUR manifest machine row "unavailable — no sysinfo binary configured"

§0 The ruling this plan realises

Owner, 2026-09-01. The machine row (top-like readings) is infrastructure, owned by AUR — a project binary must never be the thing that lights it. Scheduling thresholds are standard across the board: free-resource requirements and warning-vs-block levels are one definition, identical for every project. Typical rustc compile overhead is likewise a standard figure. Only expected-overhead projections — what a specific job is anticipated to cost — are project-local. And each doc-server instance lists its own server process in its own Console tab: AUR's console shows the doc server; MTI's shows the doc server alongside the MTI daemons.

§1 What happens today

The manifest's machine row is fed by SysinfoStream (server/server.py:1609), which spawns whatever binary the project's server.config.json names under sysinfo_bin. MTI names tools/bin/mti-tier, whose sysinfo subcommand streams readings and the thresholds from resources::Policy (rust/launcher/src/resources.rs:568) — the same policy MTI's admission gates (rustc-gate, mti-gate, cc-gate) apply. AUR ships no such binary, so its own manifest — the infrastructure project's — is the one that says "unavailable". The thresholds are thus defined in a project, and the infrastructure borrows them: ownership inverted relative to the ruling. Separately, the doc server itself appears in no console, and its ensure-script launches it with >/dev/null 2>&1, so a mid-session death (observed today, MTI instance, post-reboot) leaves zero evidence.

§3 AUR work items

A1 — Built-in /proc sampler replaces the spawned binary

Before: no sysinfo_bin → no machine row. After: every manifest renders the row, unconfigured.

A sampler thread in server.py reads /proc itself on the existing 3-second interval: load and runnable from /proc/loadavg, CPU percentages as a delta between successive /proc/stat reads (the reason the current design is long-lived holds identically for a thread), MemAvailable/MemTotal from /proc/meminfo, swap si/so as a rate from /proc/vmstat deltas — the P11 watch-the-machine field set. It feeds the same _SYSINFO dict in the same k=v field shape, so system_stats(), staleness handling and the row's rendering are untouched. Pure Python, no build step, inherited by every project instantly through the shared-root symlink.

A2 — Standard policy file at the shared root

~/.local/aur/policy.json, authored in AUR, deployed version-suffixed behind the stable name by the same mechanism as ann.js. Contents: memory reserve, free-core requirement, disk reserve, min_idle_pct, max_iowait_pct, warn-vs-block levels for the row's colouring, the nice ladder, and typical rustc per-unit overhead. Initial values are MTI's current measured ones (owner-settled 2026-07-31: 15% idle, 0.8% iowait) — the values move home; nothing is re-derived.

server.py judges the row against this file directly (warn/block colouring), replacing the threshold fields the spawned binary used to embed in its stream.

A3 — Server self-registration + a real log

Before: the doc server appears in no console and dies without evidence. After: each instance's Console tab carries a "doc-server" row — name, pid, log — and the log doubles as the crash evidence that was missing today.

Two halves, one item because the row needs a log to point at: (1) the ensure-script and the folderOpen task redirect the server's output to a logfile beside server.port instead of /dev/null; (2) on bind, the server writes a descriptor for itself into its own console registry and removes it on clean shutdown (P8 — it owns its lifecycle end to end). AUR's instance, whose daemon_dir/registry are unset, gets a default registry under its own state dir so the row renders there too.

A4 — Retire the sysinfo_bin knob

Remove the key from the config schema and SysinfoStream's binary path. A config file still carrying it gets one WARNING naming the key as retired (P14's spirit: never silently reinterpret), then is served normally. The knob's justification — "the project owns the policy" — is exactly what the ruling reversed, so no override survives.

§4 MTI work items

M1 — resources::Policy consumes the shared policy file

Policy::from_env() becomes a P16 ladder: shared-root policy.json → environment override (existing env_num/env_pct knobs, kept for experiments) → compiled default (last rung; a missing shared root must never make a gate refuse to gate). Gate behaviour is bit-identical on day one because the file's values are the ones the code compiles in today; what changes is which definition is authoritative when a knob next moves.

M2 — Retire mti-tier sysinfo and MTI's sysinfo_bin config line

The subcommand's only consumer was the doc server. Remove it, its usage lines, and the sysinfo_bin entry in aur/server.config.json. Demand, the gates, and every other mti-tier mode are untouched.

M3 — Tests (fail-first, both repos)

AUR: sampler unit checks (field presence, delta correctness against a fixture pair of /proc snapshots, staleness), policy-file parse + ladder fallback, self-registration row appearing in /consoles and disappearing on shutdown — extending tests/test_console_streams.py's pattern. MTI: Policy ladder precedence (file beats default, env beats file), and a red-first test that the retired knob warns. Timing recorded per PROCESS §8.

§5 Sequencing and risk

Order: A1→A2 land together (the row must not go dark between them); A3, A4 follow; then M1, M2, M3. AUR-first means MTI's manifest row switches source the moment its server restarts — before M1/M2 land, MTI briefly has both the new row and the still-working old policy code, which is safe overlap, not conflict.

Environment hazards named (P15): the policy file is a session-shared resource — a half-written file must never be read (write-temp-then-rename); the sampler adds one thread to a long-lived server (readings only, no locks beyond the existing _sys_lock); self-registration touches the console registry other tooling reads (same descriptor format console-register.sh already writes). No irreversible or outward-facing actions anywhere in scope.

Explicitly out of scope: per-process top-consumers in the machine row (worth doing, separate item — needs a presentation decision), and any change to gate admission behaviour.
